# Diagnostic Proposal Intake V1

This prospective delta extends Task15's five-command CLI without changing its
historical contract, claims or evidence. Preparation is not scientific adoption,
signed admission, immutable registration, financial permission or launch.
Coding-subscription authorization is not Diagnostic-science or API authorization.

## Pending Task11 Input

The existing `register --scope PROPOSAL --eligibility ELIGIBILITY --budget-binding
BUDGET --execution-approval APPROVAL --output-dir DIR` recognizes the genuine
`phase13-task11-proposed16-v1` proposal. It verifies the fixed task/baseline/arm/seed
order, four common-prefix groups, common D_cal inputs and DC raw-interaction order,
renderer, serialization and byte hashes. Unsupported schedules, including128,
are refused explicitly. No prefix timing, state, rendering or price is inferred.

Without complete supplied preparation and admission, exit2 returns a versioned
`phase13_diagnostic_proposal_result_v1` with `PENDING_PREREQUISITES`, the16-unit
schedule and exact field paths/codes. The genuine pending eligibility file stays
pending; its booleans cannot become signatures. This result is not a verdict
that later financial or launch gates have executed. No client, count, embedding
construction, operational registration or ledger is created.

## Complete Metadata

Add `--preparation FILE` with schema
`phase13_diagnostic_proposal_preparation_v1`. Its required fields are:

- `proposal`: exact file-byte `FilePin` for the frozen proposal.
- `subject`: a complete existing `phase13_diagnostic_cli_subject_v1` value supplied
  as typed runtime metadata, not a proposal relabelled as a subject. All native
  inputs/states, resources, sources, child identities, paths and80 existing
  count/generation operation plans must already be supported by supplied facts.
- `groups`: four ordered `GroupFacts`, each identifying `group_id`, `prefix_id`,
  `source_identity`, `checkpoint_id`, `checkpoint_index`, `prefix_sample_ids`,
  `state_binding` and `evidence` pins. These must match the actual native branches
  and clean state; nonnull frozen facts cannot be replaced. Suffix inputs must
  not occur in the supplied prefix sample inventory.
- `renders`: explicit `RenderFacts` (`unit_id`, `renderer_id`, `render_id`,
  `evidence`) where frozen native rendering identities are missing. Existing
  frozen DC identities/triplets cannot be substituted.

Proposal, inventory, family, state and supplementary evidence pins must occur in
the subject's source closure and reopen unchanged. The adapter matches every
native task/input, baseline, arm, seed, group and render; it does not fabricate
the remaining subject fields or sign anything. `prepare_proposal()` returns the
canonical supplied subject as `PREPARED_NOT_ADMITTED` only after those checks.
Null frozen fields describe missing facts, not authority to reconstruct them.
Attributable admissibility remains the scientific admission role's responsibility.

Preparation also binds each DC declaration to the unique selected injected entry
in the supplied checkpoint, including candidate, branch triplet, actual entry
render, query, raw response, serialized bytes and content hash. The existing DC
serializer/validator must reproduce the entire checkpoint from its consumed
archive and strategy state. Missing selected payload facts refuse explicitly;
matching labels or recomputed proposal hashes alone are insufficient. Existing
parent/curator carrier laws are not changed or waived.

Canonical input signatures are recomputed using the existing MEB input parser,
NFC word-multiset law and canonical signature serialization, and joined to the
exact indexed row of the pinned input inventory. Embedding identity, revision,
dimension and normalization must equal the BGE contract consumed by the existing
native loader/runtime, without constructing an embedding provider. These checks
do not establish cache availability, native qualification or scientific approval.

The metadata explicitly reuses the existing typed subject instead of introducing
a parallel subject builder or executor. Genuine setup/prefix work must be lawful
already evidenced reuse or separately accounted preparation; the fixed80
ordinary operations do not waive additional liabilities or authorize setup.

## Admission And Registration

`--eligibility` must then provide the existing detached `AdmissionEvidence`, with
authentic science, launch and credential/account statements for the exact subject
digest. The explicit budget and approval paths must still match the subject and
launch evidence. The CLI calls the unchanged `register()` function; all trusted
role separation, current-source, account, price, schedule and cap gates remain.
New intake source files are included in the current CLI source closure. Prior
registrations/pins are never silently refreshed.

`--scope SUBJECT --eligibility ADMISSION` legacy intake and `--registration
CANDIDATE` remain available. `preflight`, `run`, `verify` and `report` retain their
existing behavior. Run-time exact child/digest/credential and financial gates
remain separate from preparation and registration.

## Verification Boundary

`tests/test_phase13_proposal_intake.py` reuses retained Task15 synthetic metadata
and the exact Task11 external proposal. It skips those fixture-dependent checks
when the named external evidence tree is not installed. No native producer/BGE
rerun is required for the new tests. Positive QA creates only disposable signed
metadata and a synthetic registration under injected in-process QA trust, then
preflights it with client, embedding and ledger creation forbidden. Operational
trust policy/provisioning and the genuine Task11 hold are unchanged.

The copied QA fixture now has an explicitly synthetic input inventory and DC byte
descriptions matching its retained native payloads. Render identities and their
scope/observation/runtime pins are updated only in disposable QA copies. Original
Task11/Task15 artifacts remain untouched. `test_phase13_proposal_payload_binding.py`
covers direct preparation and exact-subject signed CLI refusals for independent
payload, signature, inventory and resource contradictions.
